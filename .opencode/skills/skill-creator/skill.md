# Skill Creator

创建新技能并迭代改进的工作流。高层流程：

- 理解用户想要的技能
- 编写 skill.md 草稿
- 创建测试用例并运行评估
- 让用户审查结果
- 根据反馈改进技能
- 重复直到满意

你的任务是根据用户当前所处的阶段，帮他们推进。

---

## 沟通风格

用户的技术水平差异很大——有的人是第一次打开终端，有的人是资深工程师。根据对话中的上下文线索来调整表达。先花点时间理解用户真正需要什么，不要急于跳到写代码。

术语说明：
- "评估"和"基准测试"是同一回事——用测试用例验证技能效果
- 提到 JSON、断言时，确保用户真的理解这些概念再使用
- 如果不确定用户是否理解某个术语，给一句简短的定义

可以适当解释原理，而不是列出冷冰冰的 MUST 清单。用说理的方式让 LLM 理解为什么重要，比生硬的规定更有效。

## 创建技能

### 捕获意图

先理解用户意图。当前对话可能已经包含了用户想要的工作流（如"把这个做成 skill"）。如果是，先从对话历史中提取关键信息——用到的工具、步骤顺序、用户的修正、输入输出格式。

然后确认：

1. 这个技能应该让 opencode 能做什么？
2. 什么时候触发？（什么用户语境/短语）
3. 预期的输出格式是什么？
4. 是否需要设置测试用例来验证？

### 调研

主动追问边界情况、输入输出格式、示例文件、成功标准和依赖项。在写测试之前把这些问题理清楚。

如果有可用的 MCP 用于调研（查文档、找类似 skill），使用 `webfetch` 工具并行调研。做好准备再问用户，减少来回次数。

### 写 skill.md

基于用户访谈，填充以下内容：

- **name**: 技能标识符（小写字母、数字、连字符）
- **description**: 何时触发、做什么。这是主要的触发机制——描述中既要说明技能做什么，也要说明什么场景下使用。所有"何时使用"的信息放在这里，而不是正文中。注意：opencode 倾向于"欠触发"技能——即不太主动使用它们。为了应对这一点，建议描述写得稍微"推动"一些。例如，不只是"显示内部数据"，而是"显示内部数据。当用户提到仪表盘、数据可视化、内部指标，或想要展示任何公司数据时，务必使用此技能。"
- **user-invocable**: 通常设为 true

正文结构原则：
- 保持 skill.md 在 500 行以内；如果接近这个限制，增加分层结构并给出清晰的指引说明下一步去哪
- 从 references/ 中明确引用文件，指导何时阅读它们
- 对大型引用文件（>300行），包含目录表
- 对于支持多领域/框架的技能，按变体组织：

```
cloud-deploy/
├── skill.md (workflow + selection)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```

注意：opencode 只读取被相关引用的 reference 文件。

写法风格：
- 尽量用祈使句
- 需要规定输出格式时，用模板方式：

```
## 报告结构
始终使用此精确模板：
# [标题]
## 执行摘要
## 关键发现
## 建议
```

- 包含示例
- 解释为什么重要，而不是生硬地写 MUST
- 先写草稿，然后以新鲜视角审视改进

### 测试用例

写完 skill 草稿后，提出 2-3 个真实的测试 prompt——用户实际会说的那种。和用户确认："这里有一些我想尝试的测试用例，你觉得合适吗？要不要加一些？"

保存测试用例到 `evals/evals.json`：

```json
{
  "skill_name": "my-skill",
  "evals": [
    {
      "id": 1,
      "name": "descriptive-name",
      "prompt": "用户的任务 prompt",
      "expected_output": "对预期结果的描述",
      "files": [],
      "assertions": [
        "可验证的断言1",
        "可验证的断言2"
      ]
    }
  ]
}
```

断言应该在稍后评分时能被客观验证。对于主观性技能（写作风格、设计质量），评分更适合定性评估，不要强行套断言。

## 运行和评估测试

这是连续的流程——不要中途停下。**不要使用 `/skill-test` 或任何其他测试 skill。**

把结果放在 `<skill-name>-workspace/` 作为 skill 目录的兄弟目录。在工作空间内，按迭代组织（`iteration-1/`、`iteration-2/`），每次迭代内每个测试用例一个目录（`eval-0/`、`eval-1/`）。不需要预先创建所有目录——边跑边建。

### 第1步：同时启动所有运行（with-skill 和 baseline）

对于每个测试用例，同时启动两个子代理——一个带技能，一个不带。这一点很重要：不要先跑带技能的，再回头跑 baseline。一次性启动所有，让它们大致同时完成。

**带技能运行：**
```
执行此任务：
- Skill 路径：<path-to-skill>
- 任务：<eval prompt>
- 输入文件：<eval files if any，或 "none">
- 保存输出到：<workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- 需要保存的输出：<用户关心的内容，如 "最终代码文件"、".docx 文件">
```

**Baseline 运行（同一条 prompt，但不带技能）：**
- **创建新技能**: 不使用任何 skill。同一条 prompt，不给 skill 路径，保存到 `without_skill/outputs/`。
- **改进现有技能**: 旧版本。编辑前先快照 skill（`cp -r <skill-path> <workspace>/skill-snapshot/`），然后让 baseline 子代理指向快照。保存到 `old_skill/outputs/`。

每个测试用例写一个 `eval_metadata.json`：

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "用户的任务 prompt",
  "assertions": []
}
```

给每个 eval 一个基于测试内容的描述性名称，不只是"eval-0"。用这个名称作为目录名。

### 第2步：在运行期间起草断言

不要干等运行结束——这段时间可以高效利用。起草每个测试用例的量化断言并解释给用户。如果断言已经存在于 `evals/evals.json` 中，审查它们并解释每条检查什么。

好的断言是客观可验证的，有描述性名称——在基准测试查看器中应该清晰可读，让人一眼就明白每条检查什么。主观性技能（写作风格、设计质量）更适合定性评估——不要在需要人为判断的地方强行套断言。

更新 `eval_metadata.json` 和 `evals/evals.json` 中的断言。也向用户解释他们将在查看器中看到什么——包括定性输出和量化基准。

### 第3步：运行完成后捕获计时数据

每个子代理任务完成时，通知中包含 `total_tokens` 和 `duration_ms`。立即保存到运行目录的 `timing.json`：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

这是捕获这些数据的唯一机会——通知只有一次，不会被持久化。每条通知到达时立即处理，不要批量处理。

### 第4步：评分、汇总、启动查看器

所有运行完成后：

1. **评分每条运行** —— 启动 grader 子代理（读取 `agents/grader.md`），逐条断言评估输出。保存结果到 `grading.json`。
2. **汇总成 benchmark** —— 收集所有评分和计时，人工计算统计量（通过率、平均 token、平均耗时），写入 `benchmark.json`。具体 schema 见 `references/schemas.md`。
3. **生成 HTML 报告** —— 用 `write` 工具直接生成一个 `eval_viewer.html`，包含：
   - "Outputs" 标签页：逐个展示测试用例的 prompt、输出、评分结果
   - "Benchmark" 标签页：汇总统计表（通过率、耗时、token）
   - 使用内联 CSS/JS，不需要外部依赖
4. **告知用户** —— "评估结果已生成，输出保存在以下文件中。请查看后给我反馈。"
5. **读取反馈** —— 用户告诉你他们看完后，根据反馈改进技能。

## 改进技能

这是循环的核心。跑完测试用例、用户审查了结果，现在需要根据反馈让技能变得更好。

### 如何思考改进

1. **从反馈中泛化** —— 你和用户只在有限的几个例子上反复迭代。如果技能只在这些例子上 work，那没有用。不要做过度适配的小修小改，也不要生硬地加 MUST。如果某个问题很顽固，试试换不同的元方法或工作模式。

2. **保持 prompt 精炼** —— 去除没有发挥作用的部分。真正读 transcript（不要只看最终输出）——如果技能让模型花大量时间做无产出的事情，果断去掉那些部分。

3. **解释为什么** —— 努力解释你要求模型做的每一件事的"为什么"。今天的 LLM 很聪明，给一个好的方向比死板的指令更有效。即使反馈是负面的或沮丧的，试着真正理解任务和用户为什么写他们写的东西，然后把这种理解转化成指令。

4. **寻找跨用例的重复工作** —— 读 transcript，如果所有子代理都独立地写了类似的辅助脚本或采用了相同的多步方法，这是强烈信号：技能应该把那个脚本打包好放在 `scripts/` 里。一次写好，以后每次调用都省去重新发明的轮子。

### 迭代循环

改进技能后：

1. 把改进应用到技能文件
2. 将所有测试用例重新运行到新的 `iteration-<N+1>/` 目录，包括 baseline 运行。如果创建新技能，baseline 永远是 `without_skill`——跨迭代不变。如果改进现有技能，用你的判断决定 baseline：原始版本或上一次迭代。
3. 用 `--previous-workspace` 指向上一轮生成查看器
4. 等待用户审查并告诉你他们完成了
5. 读新反馈，再次改进，重复

持续直到：
- 用户说他们满意
- 反馈全是空的（看起来都不错）
- 没有取得有意义的进展

## 描述优化

技能 frontmatter 中的 `description` 字段是决定 opencode 是否调用技能的主要机制。创建或改进技能后，主动提出优化描述以提高触发准确性。

### 第1步：生成触发评估查询

创建 20 条评估查询——混合应触发和不应触发的。查询必须是真实用户在 opencode 中会实际输入的内容，而不是抽象请求。包含文件路径、个人背景信息、公司名称、URL 等。有些可以小写、含缩写、打字错误或口语化表达。

好的应触发查询需要覆盖面广——同样的意图用不同措辞表达，有些正式有些随意。包含用户没有明确提技能名但显然需要它的场景。包含一些和另一个技能竞争但应该胜出的场景。

好的不应触发查询应该是"差点命中"——和技能共享关键词或概念但实际上需要别的东西。想想邻近领域、模糊措辞、关键词命中但实际无关的场景。

```json
[
  {"query": "用户的 prompt", "should_trigger": true},
  {"query": "另一个 prompt", "should_trigger": false}
]
```

### 第2步：用户审查

生成一个简单的 HTML 页面展示所有 20 条查询，每条带有开关让用户切换 should_trigger，然后可以导出为 JSON。用 `write` 工具直接写 HTML，打开文件让用户审查。

### 第3步：手动优化

根据用户确认后的数据集，分析哪些查询匹配错了，手动调整 description 措辞。

提示词优化技巧：
- 如果太多假阳性（不应触发却触发了）：增加限定条件，明确排除场景
- 如果太多假阴性（应触发却没触发）：强化关键词，增加同义表达
- 检查描述是否过于狭窄或过于宽泛

调整后用用户确认的 20 条查询重新验证，直到满意。
