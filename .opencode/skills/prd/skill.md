# PRD Skill for OpenCode

## 概述

此 skill 提供两个核心功能：
1. **生成 PRD** - 从功能描述创建结构化产品需求文档
2. **转换 PRD** - 将 markdown PRD 转换为 Ralph 可执行的 prd.json 格式

## 触发条件

当用户说以下任一内容时，加载此 skill：

**生成 PRD：**
- "创建 PRD"
- "生成 PRD"
- "为 XXX 写 PRD"
- "规划这个功能"
- "编写需求文档"

**转换 PRD：**
- "转换 PRD 为 Ralph 格式"
- "创建 prd.json"
- "转换为 prd.json"
- "生成 Ralph JSON"

---

## 功能一：生成 PRD

### 流程

1. **接收功能描述** - 从用户获取功能描述
2. **询问澄清问题** - 提出 3-5 个关键问题（带字母选项）
3. **生成 PRD** - 基于回答生成结构化文档
4. **保存文件** - 保存到 `tasks/prd-[feature-name].md`

**重要：** 只创建 PRD，不要开始实现。

### 澄清问题格式

问 3-5 个关键问题，聚焦：
- **问题/目标：** 解决什么问题？
- **核心功能：** 关键操作是什么？
- **范围/边界：** 不应该做什么？
- **成功标准：** 如何判断是否完成？

```
1. 这个功能的主要目标是什么？
   A. 改善用户注册体验
   B. 提高用户留存率
   C. 减少支持负担
   D. 其他：[请说明]

2. 目标用户是谁？
   A. 仅新用户
   B. 仅现有用户
   C. 所有用户
   D. 仅管理员

3. 范围是什么？
   A. 最小可行版本
   B. 全功能实现
   C. 仅后端/API
   D. 仅前端 UI
```

用户可以用 "1A, 2C, 3B" 格式快速回复。

### PRD 结构

生成的 PRD 包含以下部分：

#### 1. 简介/概述
简述功能及其解决的问题。

#### 2. 目标
具体、可衡量的目标（项目符号列表）。

#### 3. 用户故事
每个故事包含：
- **标题：** 简短描述性名称
- **描述：** "作为 [用户]，我想要 [功能]，以便 [收益]"
- **验收标准：** 可验证的完成清单

每个故事应足够小，可以在一次专注会话中完成。

**格式：**
```markdown
### US-001: [标题]
**描述：** 作为 [用户]，我想要 [功能]，以便 [收益]。

**验收标准：**
- [ ] 具体的可验证标准
- [ ] 另一个标准
- [ ] Typecheck/lint 通过
- [ ] **[仅 UI 故事]** 使用 dev-browser skill 在浏览器中验证
```

**重要：**
- 验收标准必须可验证，不能模糊。"正常工作" 是坏标准。"删除前按钮显示确认对话框" 是好标准。
- **对于任何有 UI 变更的故事：** 始终包含 "使用 dev-browser skill 在浏览器中验证" 作为验收标准。

#### 4. 功能需求
编号的功能列表：
- "FR-1: 系统必须允许用户..."
- "FR-2: 当用户点击 X 时，系统必须..."

要明确且无歧义。

#### 5. 非目标（范围外）
此功能不包含的内容。对管理范围至关重要。

#### 6. 设计考虑（可选）
- UI/UX 需求
- 链接到可用的模型图
- 要重用的相关现有组件

#### 7. 技术考虑（可选）
- 已知约束或依赖
- 与现有系统的集成点
- 性能需求

#### 8. 成功指标
如何衡量成功？
- "将完成 X 的时间减少 50%"
- "将转化率提高 10%"

#### 9. 待解决问题
剩余问题或需要澄清的领域。

### 输出

- **格式：** Markdown (`.md`)
- **位置：** `tasks/`
- **文件名：** `prd-[feature-name].md`（kebab-case）

### PRD 示例

```markdown
# PRD: 任务优先级系统

## 简介

为任务添加优先级，让用户能够专注于最重要的事项。任务可以标记为高、中、低优先级，通过视觉指示器和过滤功能帮助用户有效管理工作量。

## 目标

- 允许为任何任务分配优先级（高/中/低）
- 在任务卡片上提供清晰的优先级视觉区分
- 启用按优先级过滤和排序
- 新任务默认设为中优先级

## 用户故事

### US-001: 添加优先级字段到数据库
**描述：** 作为开发者，我需要存储任务优先级，以便它在会话间持久化。

**验收标准：**
- [ ] 向 tasks 表添加 priority 列：'high' | 'medium' | 'low'（默认 'medium'）
- [ ] 成功生成并运行迁移
- [ ] Typecheck 通过

### US-002: 在任务卡片上显示优先级指示器
**描述：** 作为用户，我希望一目了然地看到任务优先级，以便知道什么需要优先处理。

**验收标准：**
- [ ] 每个任务卡片显示彩色优先级徽章（红色=高，黄色=中，灰色=低）
- [ ] 无需悬停或点击即可看到优先级
- [ ] Typecheck 通过
- [ ] 使用 dev-browser skill 在浏览器中验证

### US-003: 在任务编辑中添加优先级选择器
**描述：** 作为用户，我希望在编辑任务时更改任务的优先级。

**验收标准：**
- [ ] 任务编辑模态框中的优先级下拉菜单
- [ ] 显示当前优先级为选中状态
- [ ] 选择更改时立即保存
- [ ] Typecheck 通过
- [ ] 使用 dev-browser skill 在浏览器中验证

### US-004: 按优先级过滤任务
**描述：** 作为用户，我希望过滤任务列表，以便在我专注时只看到高优先级项目。

**验收标准：**
- [ ] 过滤下拉菜单选项：全部 | 高 | 中 | 低
- [ ] 过滤条件保存在 URL 参数中
- [ ] 没有任务匹配过滤条件时的空状态消息
- [ ] Typecheck 通过
- [ ] 使用 dev-browser skill 在浏览器中验证

## 功能需求

- FR-1: 向 tasks 表添加 `priority` 字段（'high' | 'medium' | 'low'，默认 'medium'）
- FR-2: 在每个任务卡片上显示彩色优先级徽章
- FR-3: 在任务编辑模态框中包含优先级选择器
- FR-4: 在任务列表头部添加优先级过滤下拉菜单
- FR-5: 在每个状态列内按优先级排序（高到低到中）

## 非目标

- 没有基于优先级的通知或提醒
- 没有基于截止日期的自动优先级分配
- 没有子任务的优先级继承

## 技术考虑

- 重用现有的徽章组件，带有颜色变体
- 过滤状态通过 URL 搜索参数管理
- 优先级存储在数据库中，不计算

## 成功指标

- 用户可以在 2 次点击内更改优先级
- 高优先级任务立即在列表顶部可见
- 任务列表性能无回归

## 待解决问题

- 优先级是否应影响列内任务排序？
- 是否应添加优先级更改的键盘快捷键？
```

### 生成前检查清单

保存 PRD 之前：
- [ ] 提出了带字母选项的澄清问题
- [ ] 整合了用户的回答
- [ ] 用户故事小而具体
- [ ] 功能需求编号且无歧义
- [ ] 非目标部分定义了清晰的边界
- [ ] 保存到 `tasks/prd-[feature-name].md`

## 功能二：转换 PRD 为 prd.json

### 流程

将现有的 markdown PRD 转换为 `prd.json` 格式，供 Ralph 循环使用。

### 输出格式

```json
{
  "project": "[项目名称]",
  "branchName": "ralph/[feature-name-kebab-case]",
  "description": "[PRD 标题/简介中的功能描述]",
  "userStories": [
    {
      "id": "US-001",
      "title": "[故事标题]",
      "description": "作为 [用户]，我想要 [功能]，以便 [收益]",
      "acceptanceCriteria": [
        "标准 1",
        "标准 2",
        "Typecheck 通过"
      ],
      "priority": 1,
      "passes": false,
      "notes": ""
    }
  ]
}
```

### 故事大小：第一规则

**每个故事必须能在一次 Ralph 迭代（一个上下文窗口）中完成。**

Ralph 每次迭代启动一个全新的 AI 实例，没有之前工作的记忆。如果故事太大，LLM 会在完成之前耗尽上下文，产生损坏的代码。

#### 合适大小的故事：
- 添加数据库列和迁移
- 向现有页面添加 UI 组件
- 用新逻辑更新服务器操作
- 向列表添加过滤下拉菜单

#### 太大（需要拆分）：
- "构建整个仪表板" - 拆分为：schema、查询、UI 组件、过滤器
- "添加身份验证" - 拆分为：schema、中间件、登录 UI、会话处理
- "重构 API" - 每个端点或模式拆分成一个故事

**经验法则：** 如果无法用 2-3 句话描述变更，就太大了。

### 故事排序：依赖优先

故事按优先级顺序执行。早期故事不能依赖后期故事。

#### 正确顺序：
1. Schema/数据库变更（迁移）
2. 服务器操作 / 后端逻辑
3. 使用后端的 UI 组件
4. 聚合数据的仪表板/汇总视图

#### 错误顺序：
1. UI 组件（依赖尚不存在的 schema）
2. Schema 变更

### 验收标准：必须可验证

每个标准必须是 Ralph 可以检查的，而不是模糊的。

#### 好的标准（可验证）：
- "向 tasks 表添加 `status` 列，默认 'pending'"
- "过滤下拉菜单选项：全部、活跃、已完成"
- "点击删除显示确认对话框"
- "Typecheck 通过"
- "测试通过"

#### 坏的标准（模糊）：
- "正常工作"
- "用户可以轻松完成 X"
- "良好的用户体验"
- "处理边缘情况"

#### 始终包含作为最终标准：
```
"Typecheck 通过"
```

对于有逻辑可测试的故事，还包含：
```
"测试通过"
```

#### 对于更改 UI 的故事，还包含：
```
"使用 dev-browser skill 在浏览器中验证"
```

前端故事在视觉验证之前不算完成。Ralph 将使用 dev-browser skill 导航到页面，与 UI 交互，并确认更改有效。

### 转换规则

1. **每个用户故事变成一个 JSON 条目**
2. **ID：** 顺序编号（US-001, US-002, 等）
3. **优先级：** 基于依赖顺序，然后按文档顺序
4. **所有故事：** `passes: false` 和空 `notes`
5. **branchName：** 从功能名称派生，kebab-case，前缀 `ralph/`
6. **始终添加：** 将 "Typecheck 通过" 添加到每个故事的验收标准

### 拆分大型 PRD

如果 PRD 有大型功能，拆分它们：

**原始：**
> "添加用户通知系统"

**拆分为：**
1. US-001: 向数据库添加通知表
2. US-002: 创建用于发送通知的通知服务
3. US-003: 向页头添加通知铃铛图标
4. US-004: 创建通知下拉面板
5. US-005: 添加标记为已读功能
6. US-006: 添加通知首选项页面

每个都是可以独立完成和验证的专注变更。

### 归档之前的运行

**在写入新的 prd.json 之前，检查是否存在来自不同功能的现有 prd.json：**

1. 读取当前的 `prd.json`（如果存在）
2. 检查 `branchName` 是否与新功能的分支名称不同
3. 如果不同且 `progress.txt` 有超出头部的内容：
   - 创建归档文件夹：`archive/YYYY-MM-DD-feature-name/`
   - 将当前的 `prd.json` 和 `progress.txt` 复制到归档
   - 用新的头部重置 `progress.txt`

### 保存前检查清单

写入 prd.json 之前，验证：
- [ ] **之前的运行已归档**（如果 prd.json 存在且 branchName 不同，先归档）
- [ ] 每个故事可以在一次迭代中完成（足够小）
- [ ] 故事按依赖关系排序（从 schema 到后端到 UI）
- [ ] 每个故事都将 "Typecheck 通过" 作为标准
- [ ] UI 故事将 "使用 dev-browser skill 在浏览器中验证" 作为标准
- [ ] 验收标准可验证（不模糊）
- [ ] 没有故事依赖后期故事

## 为初级开发者写作

PRD 的读者可能是初级开发者或 AI agent。因此：
- 明确且无歧义
- 避免行话或解释它
- 提供足够的细节以理解目的和核心逻辑
- 对需求编号以便轻松引用
- 在有帮助的地方使用具体示例
