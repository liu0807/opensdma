# Code Reviewer Skill for Ralph Loop

## 概述

每轮 Ralph 循环完成后对代码进行独立检视。采用**语义分析驱动**的多阶段流程：先扫描代码变更特征，按需激活检视维度，逐条构建证据链，由独立挑战者验证每条发现。只有检视通过才能进入下一轮。

**参考规则文件**：
- `references/user-mode-rules.md` — 细粒度用户态检视规则（D1-D11），按代码模式激活
- `references/kernel-mode-rules.md` — 内核态检视规则（K1-K8），**仅当检测到内核模式时激活**

## 核心原则

1. **独立检视** — 使用 `task` 工具启动全新的检视 sub-agent
2. **语义驱动** — 不固定检视维度，根据代码变更特征动态激活。从 `references/user-mode-rules.md` 的触发模式中匹配实际代码
3. **证据链** — 每个发现必须包含存在性/影响性/触发条件/保护排除 4 点证据
4. **挑战验证** — 独立 sub-agent 逐条挑战每条发现的真实性，减少误报
5. **闭环修复** — 检视不通过时启动修复 sub-agent，最多重试 3 次

## 检视流程

```
检视循环:
  1. 读取 prd.json + progress.txt + git diff
  2. 启动检视 agent（4 阶段流程）
     Phase 1 → 代码特征扫描（匹配 rules 的触发模式）
     Phase 2 → 根据特征激活 rules 对应维度
               - 用户态: 读 references/user-mode-rules.md → 激活匹配的 D1-D11
               - 内核态: 检测到内核模式 → 读 references/kernel-mode-rules.md → 激活 K1-K8
     Phase 3 → 逐条构建 4 点证据链
     Phase 4 → 生成检视报告
  3. PASS → 进入下一轮
     FAIL → 启动挑战验证 agent
  4. 挑战验证后：
     无确认问题 → 视为 PASS
     仍有确认问题 → 启动修复 agent（传递检视+挑战结果）
  5. 修复后重新检视（最多 3 次）
  6. 超限 → 记录问题到 progress.txt，继续下一轮
```

### 主控制逻辑

```
1. 读取 prd.json → 刚完成的故事 ID
2. 读取 progress.txt → 实现内容
3. 查看 git diff（HEAD~1 或 --cached）
4. 启动检视 agent（全新上下文） → 等待结果
5. 解析 PASS/FAIL
   PASS → 更新 progress.txt，进入下一轮
   FAIL → 启动挑战验证 agent
6. 挑战验证后：
   无确认问题 → 视为 PASS
   仍有确认问题 → 启动修复 agent
7. 修复后 → 重新检视（最多 3 次）
8. 超限 → 记录问题到 progress.txt，继续下一轮
```

## 检视 Agent 任务指令

每次启动检视 agent 时，传递以下指令。检视 agent 只评估不修改代码。

```
你是一个专业的代码检视 agent，正在检视 Ralph 循环最近一轮的代码实现。

## 重要：你是全新实例
- 你没有任何之前迭代的记忆
- 只通过以下文件获取上下文：
  - prd.json（查看刚完成的故事的验收标准）
  - progress.txt（了解实现内容）
  - git diff 或变更的文件

## 检视流程（4 阶段，必须按顺序执行）

### Phase 1: 代码特征扫描

读取代码变更，识别使用了哪些 API、模式和结构。

**扫描以下类别**（从 references/ 规则文件中匹配触发模式）：
- **内存操作**: malloc/calloc/free/strcpy/memcpy/mmap
- **SDMA API**: sdma_alloc_chn/sdma_copy_data/sdma_icopy_data 等
- **并发**: pthread_mutex/__sync_*/fork/shmget
- **文件/设备**: open/close/ioctl
- **输入**: getopt_long/strtol/atoi
- **结构**: 新增函数/文件/结构体/全局变量

**内核模式检测**: 如检测到 copy_from_user/kmalloc/spin_lock/file_operations/module_init 等，标记"检测到内核代码模式"

输出特征扫描结果供 Phase 2 使用。

### Phase 2: 按需激活检视维度

根据 Phase 1 扫描结果，从 `references/user-mode-rules.md` 中激活匹配的检视维度（D1-D11）。**只激活与代码变更相关的维度**。

如果 Phase 1 检测到内核代码模式，额外从 `references/kernel-mode-rules.md` 中激活对应内核维度（K1-K8）。

激活规则依据：
- 每个维度有 **触发模式** 列表 → 代码匹配则激活
- 激活后执行对应维度的 **检查清单** 中的所有项
- 严重等级参考规则文件中的 **严重等级指南**

始终激活：**验收标准检查**（对照 prd.json 当前故事的 acceptanceCriteria）

### Phase 3: 构建证据链

对每个发现的问题，必须构建完整的 4 点证据链：

```
1. 存在性证据：代码中哪一行（文件:行号）存在什么问题
2. 影响性证据：为什么这是问题，可能触发什么后果
3. 触发条件：什么执行路径/外部输入会触发此问题
4. 保护排除：代码中已有的保护措施为什么不构成足够防御
```

### Phase 4: 生成检视报告

输出必须遵循以下模板。

```
## 代码特征扫描
- 内存操作模式：[...]
- SDMA API模式：[...]
- 并发/同步模式：[...]
- 文件/设备模式：[...]
- 输入处理模式：[...]
- 结构设计模式：[...]
- 内核模式：[ detected / none ]

## 激活的检视维度
- [D1 动态内存管理] - 激活理由：[检测到 malloc/calloc]
- [D3 文件描述符管理] - 激活理由：[检测到 open/ioctl]
  ...（仅列出已激活的维度）

## 激活的内核态规则（如有）
- [K1 用户/内核内存传输] - 激活理由：[检测到 copy_from_user]
  ...（仅在检测到内核模式时出现）

## 验收标准检查
- [ ] 标准 1 - [通过/未通过] - [说明]
- [ ] 标准 2 - [通过/未通过] - [说明]

## 问题详情（按严重等级排序）

### [序号]. [问题标题] @ [文件:行号]
**严重等级**: CRITICAL / HIGH / MEDIUM / LOW
**检视维度**: [D1-D11 或 K1-K8]

**证据链**:
1. [存在性] [具体代码位置和内容]
2. [影响性] [可能导致的后果]
3. [触发条件] [触发路径和条件]
4. [保护排除] [已有保护为什么不充分]

**修复建议**:
[具体可操作的修复代码或步骤]

---

### [序号]. [问题标题] @ [文件:行号]
...

## 检视结论
**状态**: PASS / FAIL
**已确认问题数**: N（CRITICAL: X, HIGH: Y, MEDIUM: Z, LOW: W）

PASS 条件：
- 无 CRITICAL 或 HIGH 等级的问题
- LOW/MEDIUM 问题不超过 3 个（strict 模式下不允许任何问题）
```

## 挑战验证 Agent 指令

检视 agent 返回 FAIL 后，启动挑战验证 sub-agent：

```
你是一个独立的检视挑战 agent。逐条挑战检视报告中的每个发现，验证其是否为有效问题。

## 核心原则
1. 独立验证：不依赖检视 agent 的结论，基于代码原始上下文独立验证
2. 逐条挑战：每个发现必须单独验证
3. 证据说话：所有结论必须有具体代码支持

## 挑战流程

### 第1步：回读原始代码
对每个发现，用 Read 工具读取问题行号附近（+/-5 行）的代码。

### 第2步：逐条验证证据链

**存在性验证**：代码中确实存在所述代码？行号准确？描述一致？
**影响性验证**：后果真的可能发生？是否遗漏了已有的保护？
**触发条件验证**：触发路径在当前业务场景下是否可达？
**保护排除验证**：代码中是否有检视者遗漏的保护？

### 第3步：输出挑战结果
```
## 挑战验证结果

### 挑战 #[序号]: [问题标题] @ [文件:行号]
**原严重等级**: [CRITICAL/HIGH/MEDIUM/LOW]
**挑战结论**: ✓ 已确认 / ✗ 已推翻 / ? 待确认
**理由**: [具体分析每条证据链是否成立]
```

### 挑战结论规则
- ✓ 已确认：证据链完整，问题有效
- ✗ 已推翻：证据链不成立
- ? 待确认：部分成立但缺少上下文

### 汇总
```
## 挑战汇总
- 总发现数：N
- ✓ 已确认：X | ✗ 已推翻：Y | ? 待确认：Z
- 状态：PASS / FAIL（仍有确认问题）
```
```

## 修复 Agent 任务指令

挑战验证后仍有确认问题时启动：

```
你是一个代码修复 agent，正在修复检视中发现的问题。

## 上下文
- prd.json（故事要求）
- progress.txt（之前实现）
- 检视反馈（见下方）

## 检视反馈（含挑战验证结果）
[粘贴完整的检视报告 + 挑战验证结果，只含 ✓ 已确认 的问题]

## 你的任务
1. 理解问题：阅读已确认问题的证据链
2. 修复代码：按修复建议修改，只修改确认问题
3. 验证修复：确认所有问题已修复
4. 更新 progress.txt
5. 结束：说明修复了哪些问题
```

## 检视结果处理

### 检视通过
```
✓ US-XXX 检视通过
   - 所有验收标准已满足
   - 代码质量良好
   → 进入下一轮循环
```

### 检视未通过
```
✗ US-XXX 检视未通过
   确认问题：
   - [CRITICAL] [问题1]
   - [HIGH] [问题2]
   启动修复 agent...
```

### 达最大重试次数
```
✗ US-XXX 检视失败（已达最大重试次数）
   确认问题：[最后的问题列表]
   记录到 progress.txt，继续下一轮...
```

## 与 Ralph Skill 的集成

```
WHILE 迭代计数 <= 最大迭代次数:
  1. 启动 Ralph 子 agent 实现故事
  2. 等待完成
  3. 启动检视流程（reviewer skill）
     3.1 检视 agent → PASS？→ 继续
     3.2 挑战验证 → 确认问题？→ 继续
     3.3 修复 agent → 重新检视（最多 3 次）
  4. 汇报进度
  5. 迭代计数 += 1
```

## 检视标准配置

项目根目录 `reviewer-config.json`（可选，不存在时使用默认值）：

```json
{
  "strictness": "normal",
  "maxRetries": 3
}
```

- **strictness**: `lenient` 忽略 MEDIUM/LOW；`normal` 不允许 CRITICAL/HIGH；`strict` 不允许任何问题
- **maxRetries**: 修复 agent 最大重试次数

## 边界情况处理

- **无代码变更**：检视直接通过
- **检视 agent 异常**：记录错误，默认视为通过
- **挑战验证异常**：记录错误，以检视 agent 原始结果为准
- **修复 agent 异常**：记录错误，重试或跳过
- **最大重试超限**：记录问题到 progress.txt，继续下一轮
- **git diff 失败**：退而使用 `git diff --cached` + `git status`
- **未检测到任何代码模式**：只检查验收标准 + 设计质量维度（D11）
- **规则文件缺失**：使用 skill 内联默认规则（见"默认检视维度"节）

## 默认检视维度

当 `references/user-mode-rules.md` 不可用时，回退到以下内联规则：

1. **内存安全** — malloc 检查 NULL？free 配对？strcpy 安全？
2. **并发安全** — 锁保护共享数据？init/destroy 配对？
3. **API 正确性** — SDMA API 返回值检查？参数类型正确？
4. **输入验证** — 外部参数校验？数组越界？整数溢出？
5. **设计质量** — 命名约定？死代码？函数职责单一？
